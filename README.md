# ContractSense 🇮🇳

> **India-aware contract review prototype**

ContractSense is an informational, AI-assisted review workspace for contracts. The repository contains a FastAPI backend, a browser UI served by that API, and a Flutter/Riverpod/Dio client source tree. The default local configuration uses SQLite, a transparent keyword clause-classification baseline, lexical contract retrieval, versioned legal review prompts, evidence-only fallback chat, and generated PDF reports.

> **Legal and technical status:** This is a prototype, not legal advice or a production-validated legal/compliance system. The optional transformer adapter loads only a locally supplied fine-tuned sequence-classification checkpoint (for example, LegalBERT if that is the supplied model); no trained checkpoint, accuracy claim, lawyer validation, complete Indian legal corpus, or complete state-law coverage is included. The optional Chroma integration currently uses deterministic hashed-token vectors, not a validated semantic embedding model. Read the coverage and limitations sections before using results.

## Quick start (local web app + API)

Requires Python 3.11 or newer. Run from the repository root:

```bash
python3.11 -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell: .venv\\Scripts\\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r backend/requirements-dev.txt
cp .env.example .env   # Windows: copy .env.example .env
```

Edit `.env` and set a private random `SECRET_KEY` before exposing the API. For local work, the defaults need no MongoDB, hosted LLM key, or model download. Start the backend and integrated web app:

```bash
python -m uvicorn backend.app.main:app --reload --host 0.0.0.0 --port 8000
```

Open <http://127.0.0.1:8000>. API documentation is at <http://127.0.0.1:8000/docs>; health/configuration status is at <http://127.0.0.1:8000/api/v1/health>. Create a local account, upload a document you are authorized to use, and inspect the analysis, source links, coverage notes, chat evidence, and report.

### Flutter client

Flutter SDK is not installed in every development environment. The repository includes the Dart app and `pubspec.yaml`; platform runner directories are generated by Flutter for the platforms you target. From `frontend/`, scaffold them once and resolve the packages:

```bash
cd frontend
flutter create --project-name contractsense --platforms=android,ios,web --no-overwrite --no-pub .
flutter pub get
```

For Flutter Web, build it with a `/flutter/` base path, then start FastAPI from the repository root. FastAPI serves that build at `/flutter/`, so browser API requests stay on the same origin; do not point browser code at a localhost API URL:

```bash
flutter build web --base-href=/flutter/
cd ..
python -m uvicorn backend.app.main:app --reload --host 0.0.0.0 --port 8000
# Open http://127.0.0.1:8000/flutter/
```

For a native Android emulator, run the API in another terminal and use its host-loopback address:

```bash

```

For an iOS simulator, use `http://127.0.0.1:8000/api/v1`; for a physical device, use the backend machine's reachable LAN address. These addresses are for native development only. Production must use HTTPS. The API base URL includes `/api/v1`; it is a compile-time `--dart-define`, never an API-key location.

## 1. Project Overview

### Motivation

Contracts can contain complex payment, liability, termination, confidentiality, intellectual-property, data-protection, and dispute-resolution terms. This prototype explores a scoped first-pass review workflow for Indian users; it does not claim that existing products lack Indian support or that this implementation provides complete Indian legal coverage.

### Proposed Solution

The target architecture combines:

- **Clause segmentation and classification** with a keyword baseline by default and an optional local fine-tuned LegalBERT adapter
- **Versioned deterministic review prompts** for explicitly configured central/state source checks
- **Uncalibrated review-priority indicators**, clearly separated from model predictions and generated language
- **PyMuPDF, python-docx, and optional Tesseract OCR** for document extraction
- **SQLite by default; optional MongoDB** for application data
- **Lexical retrieval by default; optional ChromaDB using hashed-token vectors** as a retrieval prototype, not a validated semantic embedding model
- **Evidence-grounded chat and review checklists**, with Gemini/Groq/Ollama provider adapters and a no-key local fallback
- **LangChain Core prompt formatting** where installed; no claim of validated RAG performance
- **FastAPI** backend, static browser UI, and **Flutter/Riverpod/Dio** client
- **Docker** deployment example

SHAP is listed in the research specification but is not wired into the current application; installable dependencies alone do not mean that explainability is implemented.

# 2. Current system design

ContractSense is a prototype review workflow, not a trained Indian legal-analysis model. Its current hybrid pipeline combines document extraction, deterministic clause-boundary heuristics, a transparent keyword classifier, narrow source-backed review prompts, hand-set review-priority signals, contract-scoped lexical retrieval, and optional LLM providers. Optional adapters do not change the validation status of the underlying rules or model.

```text
Upload + metadata
       ↓
PDF / DOCX / TXT / image extraction (OCR when configured)
       ↓
Clause segmentation + page/source evidence
       ↓
Keyword classifier ───────┐
       ↓                    ├→ Review-priority indicators → PDF report
Legal source prompts ──────┘
       ↓
Lexical retrieval (optional Chroma hashed-token prototype)
       ↓
Evidence-only local chat OR configured Gemini/Groq/Ollama provider
```

Rule matches are deterministic text triggers, not legal conclusions. Classification labels and confidence are model/baseline outputs, not verified facts. Generated provider text is separate from both. See [limitations](#43-known-limitations) and the [coverage strategy](#14-data-and-evaluation-coverage-strategy).

# 4. Scope

The upload metadata supports NDA, employment, vendor/service, consultancy, SaaS/IT, procurement, lease/rental, data-processing, and other agreements. Metadata support is not the same as legal coverage or an agreement-specific model.

Supported upload extensions are PDF, DOCX, TXT, PNG, JPG/JPEG, and TIFF, subject to the configured size limit. Text PDFs and DOCX are extracted directly; scanned PDFs/images need a working Tesseract installation and language data. Password-protected PDFs are not supported.

The application is for issue-spotting and review assistance. It does not provide legal advice, guarantee validity/enforceability, determine final legal interpretation, or cover all Indian statutes, rules, states/UTs, or contract types. Use qualified Indian counsel for decisions.

# 5. Target users

Intended users include Indian freelancers, startups, MSMEs, and small businesses seeking a structured first-pass review. This prototype is not a substitute for a lawyer, regulated advice, or procurement/employment compliance review.

# 8. Data flow

1. An authenticated user uploads a supported document and supplies contract type, governing-law/state metadata, and optional MSME context.
2. The API validates extension/size, stores the source file, extracts text, and records extraction method, page count, and warnings.
3. Heuristic segmentation creates clause records with page/source evidence. The classifier applies keyword rules unless a compatible local checkpoint is configured.
4. The rule engine checks only configured prompts against text and supplied metadata. Findings include rule/source/version metadata; a trigger is not a legal determination.
5. The analysis combines those outputs into explicitly uncalibrated review-priority indicators. Results and retrieval chunks are persisted.
6. Chat retrieves evidence from the contract using lexical ranking (or optional hashed-token Chroma retrieval). The mock provider returns evidence-oriented fallback content; configured providers may generate text. Suggestions are review checklists, not automated legal drafting.
7. The API can produce a PDF report that carries findings, evidence, sources, and limitations.

# 10. Security and operational notes

- Passwords are hashed; API keys belong only in backend environment variables. Contract routes enforce user ownership.
- Upload extensions and byte limits are checked. This is not a malware scanner or a complete file-content security boundary.
- Uploaded originals and extracted contract text are sensitive. Configure access controls, encryption at rest, backups, retention/deletion policies, and a durable `DATA_DIR` before deployment; the prototype does not provide a full enterprise privacy program.
- Same-origin clients need no CORS; cross-origin access is disabled by default. Set explicit `CORS_ORIGINS` only for cross-origin clients. Production startup requires a non-placeholder secret of at least 32 characters and explicit non-wildcard origins. Terminate HTTPS at a trusted proxy/platform.
- Analysis and document ingestion are synchronous; OCR/large uploads can occupy a worker. Use suitable worker/process limits and timeouts for deployment.
- Do not log or expose contract text unnecessarily. Keep provider credentials server-side and send only the minimum necessary data to external providers.

# 11. Persistence model

SQLite is the zero-configuration default. Set `DB_BACKEND=mongodb` to use the optional Mongo adapter. The current repository stores users, contracts/metadata, analysis JSON, chat messages with contract evidence, legal sources, provider/limitation labels, and retrieval chunks. Compact page-to-text ranges preserve page evidence without duplicating extracted text. Uploaded originals live under `DATA_DIR/uploads`, and optional Chroma data under `DATA_DIR/chroma`.

```text
SQLite / MongoDB: users, contracts, analyses, messages, lexical chunks
Local file store: uploaded originals
Optional Chroma: contract-scoped hashed-token vectors and retrieval metadata
```

No sample account, fabricated analysis score, or user contract is bundled. The example structure above describes storage classes, not an actual result. Configure backups and verify that deletion/retention behavior matches deployment obligations.

# 12. Retrieval storage

When optional ChromaDB is installed and enabled, the current prototype persists clause text with deterministic feature-hashed token vectors and metadata such as:

```json
{
  "contract_id": "...",
  "user_id": "...",
  "clause_id": "...",
  "page": 4,
  "source": "uploaded_contract"
}
```

This vectorizer is a lightweight prototype, not a trained or validated semantic embedding model. Without ChromaDB, the backend ranks the contract's stored clauses with local lexical scoring. Neither mode has a reported retrieval benchmark. Do not describe the current behavior as production-quality semantic search.

```text
SQLite / MongoDB → users, contract metadata, analyses, messages, lexical chunks
ChromaDB          → optional contract-scoped vector copies and retrieval metadata
```

Contract deletion removes its uploaded file and primary database records; the API also attempts to delete its Chroma records. If optional vector storage is unavailable, verify storage cleanup through the Chroma operator/admin tools before production use.

# 13. Clause classifier and LegalBERT

The default backend classifier is a transparent keyword baseline. `LEGALBERT_MODEL_PATH` may point to a local Hugging Face **fine-tuned sequence-classification checkpoint** with usable `id2label` entries. The adapter reports `fine_tuned_transformer` rather than asserting the model is LegalBERT, because it does not independently verify the checkpoint's identity or training provenance. A base LegalBERT model is not treated as a trained classifier, and no checkpoint or training pipeline is bundled. Analysis records include a classifier-configuration fingerprint based on the implementation and local checkpoint file manifest; configuration drift after restart makes prior results stale. If checkpoint inference fails partway through a document, the analysis reruns all clauses with the keyword baseline so one result does not silently mix classifier engines. These are freshness/consistency aids, not model-quality validation. The UI/API report the classifier engine and confidence; baseline confidence is heuristic and uncalibrated.

A future training/evaluation flow should keep generic CUAD experiments separate from Indian-law examples and use contract-level, deduplicated train/validation/test splits. Complete Indian contracts reserved for holdout evaluation must not enter training, prompt tuning, or the development RAG index. Document label mappings, licensing, provenance, annotation review, calibration, and per-class metrics before claiming performance.

Illustrative category output only (not an actual model result):

```text
Category: Confidentiality
Confidence: not calibrated by the current keyword baseline
Engine: keyword_baseline
```

# 14. Data and evaluation coverage strategy

Keep five distinct data/source layers. Do not merge them into a single training or retrieval corpus:

1. **Generic contract-clause analysis:** CUAD and comparable public contract datasets may support general segmentation/classification experiments. The repository's `CUAD_v1/legal_contract_clauses.csv` is CUAD-derived; it is **not Indian legal coverage**. Its labels are generic clause annotations, and the added risk levels have no verified India-specific legal rationale. Do not treat those risk levels as legal truth or train an Indian legal-risk model from them without audit, provenance, contract-level splits, and validation.
2. **Indian contract examples:** collect permitted Indian NDA, employment, vendor/service, SaaS/IT, consultancy, lease/rental, procurement, and data-processing examples in a separate, access-controlled corpus. Record source, date, jurisdiction/state if known, licence/permission, document/contract ID, annotation method, annotator notes, and clause/page provenance. **No separate Indian contract examples are registered in this checkout.** Do not claim any sample contracts were processed here.
3. **Central Indian legal sources:** maintain authoritative statutes/rules, version/review date, applicability notes, source URL, and the exact rule/prompt that references each source. Legal sources are not contract examples and should not be used as model-training text by default.
4. **State-specific legal sources and rules:** keep separate per-state source/rule files. Add a state prompt only where the applicable law or administrative schedule differs; do not infer a rule from a contract's state label alone. Maharashtra currently has source-verification prompts for stamp duty and, for employment contracts, a Shops and Establishments source. A state-specific stamp-duty source prompt replaces the generic stamp-duty verification prompt only when the state rules explicitly include a stamp-duty category; unrelated state prompts do not suppress that generic verification. These prompts do not calculate duty or determine coverage. Other state coverage is not implemented yet. There is **no requirement to collect one contract per state at this stage**.
5. **Complete Indian contracts for holdout evaluation:** reserve complete, unseen Indian agreements for end-to-end evaluation. Exclude them from clause training, tuning, prompt development, and the RAG/development index. Maintain document-level separation to prevent clause leakage.

# 15. Indian legal review prompts

Rules are versioned JSON review prompts in `backend/legal_rules/central_rules.json` and `backend/legal_rules/state_rules.json`. A text trigger is deterministic; its legal implication is not. Current prompts are narrow and include restraint-of-trade language, a user-selected conditional MSMED payment review, personal-data processing, arbitration wording, electronic execution, copyright allocation, employment/labour scope, public procurement source checks, and stamp-duty source verification. Maharashtra has additional stamp-duty and employment source prompts.

These checks do not interpret the complete law, determine applicability, compute stamp duty, validate contract execution, or conclude that a term is lawful/unlawful. They preserve rule IDs, provision descriptions, official source URLs, source type/title, review date, ruleset version, matched terms, state, and selected user context where applicable. A source link does not itself validate the prompt; counsel and current-law review remain necessary.

Adding a rule requires an authoritative source, scope/applicability note, version and review date, cautious message, and positive/negative tests. Where law varies by state, add and test a separate state rule/source entry rather than generalizing from another jurisdiction. Never infer state coverage solely from a selected state field.

# 16. Risk Engine

The current review-priority score combines configured deterministic prompt severities with simple keyword/phrase heuristics for clauses. Clause classification uses the keyword baseline unless a local fine-tuned checkpoint is configured. The scoring rubric is hand-set, uncalibrated, and not evaluated; it is not a probability, legal-risk estimate, or finding that a term is unlawful. The UI and report must describe it as a review-priority indicator only.

---

# 17. Retrieval and chat

The default retriever ranks chunks from the authenticated contract with a local lexical scoring baseline. If ChromaDB is installed and enabled, a separate prototype path stores deterministic hashed-token vectors. Neither path is a validated semantic embedding/retrieval system, and no retrieval benchmark is available. The assistant is not a complete RAG system.

For the local `mock` provider, answers are evidence-oriented fallback text based on retrieved contract snippets; they are not generated legal analysis. When a hosted/local provider is configured, generated content is passed separately from retrieval evidence and can still be incorrect. Chat responses preserve source clause/page metadata where available. Do not present model text as a legal conclusion or fabricate statutory citations.

# 20. LLM provider layer

`LLM_PROVIDER=mock` is the no-key default. It supplies evidence-oriented local fallback content; suggestions are rule/category-based review checklists. Optional Gemini, Groq, and Ollama adapters can generate text when their backend-side configuration is valid. Provider errors fall back to the local response; they do not make the fallback equivalent to an LLM explanation.

Generated responses may be inaccurate, incomplete, or cite unsupported law. Contract text and chat history are untrusted input; prompts instruct providers not to follow embedded directions, but this is not a robust prompt-injection defense. API keys must remain in server environment variables; Gemini credentials are sent in a request header, not a URL or client bundle. No contract summary quality, advice quality, faithfulness, or citation accuracy has been measured. The model/provider output is distinct from deterministic rules and classifier predictions.

The checked-in `.env.example` is the canonical variable list. Copy it to `.env` in the repository root; `python-dotenv` loads it automatically, while variables already exported by a process/container take precedence. Restart the API after changing settings.

| Variable | Purpose / local default |
|---|---|
| `APP_NAME`, `APP_ENV` | Display name and environment (`ContractSense`, `development`) |
| `SECRET_KEY`, `TOKEN_TTL_HOURS` | HMAC bearer-token signing and lifetime; replace the example secret before network exposure |
| `DB_BACKEND` | `sqlite` by default; set `mongodb` only with a reachable MongoDB service |
| `MONGODB_URI`, `MONGODB_DB` | MongoDB connection settings (`lexintel` is the legacy default DB name) |
| `DATA_DIR`, `MAX_UPLOAD_MB` | Persistent database/upload/Chroma directory and upload limit |
| `LLM_PROVIDER`, `LLM_MODEL` | `mock` default (no hosted generation); supported adapters: `gemini`, `groq`, `ollama` |
| `GEMINI_API_KEY`, `GROQ_API_KEY`, `OLLAMA_BASE_URL` | Backend-only provider settings; never place provider secrets in Flutter |
| `LEGALBERT_MODEL_PATH` | Optional local, fine-tuned sequence-classification checkpoint; no model is bundled |
| `ENABLE_CHROMA` | ChromaDB is attempted when installed (default `true`); set `false` to force local lexical retrieval |
| `CORS_ORIGINS` | Comma-separated browser origins; empty by default (same-origin only); production requires explicit non-wildcard origins |
| `OCR_LANGUAGE` | Installed Tesseract language codes; default `eng` |

Generate a local secret, for example: `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Store production values in the deployment platform's secret manager, not `.env` committed to Git.

# 30. Local development

## Backend and integrated web app

From the repository root, create and activate a virtual environment:

```bash
python3.11 -m venv .venv
# Linux/macOS
source .venv/bin/activate
# Windows PowerShell
.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r backend/requirements-dev.txt
cp .env.example .env   # Windows PowerShell: Copy-Item .env.example .env
```

Edit `.env`, then run:

```bash
python -m uvicorn backend.app.main:app --reload --host 0.0.0.0 --port 8000
```

The FastAPI process serves the browser UI at `http://127.0.0.1:8000`, OpenAPI docs at `/docs`, and health/configuration at `/api/v1/health`. The API is synchronous for document ingestion and analysis; long uploads or OCR can occupy a worker. The local default is SQLite and `LLM_PROVIDER=mock`; MongoDB and external LLM accounts are not required.

### Optional OCR

Install Tesseract separately from Python dependencies, then ensure `tesseract` is on `PATH` and the selected language data is present. Examples:

```bash
# Debian / Ubuntu
sudo apt-get update && sudo apt-get install -y tesseract-ocr tesseract-ocr-eng
# macOS with Homebrew
brew install tesseract
```

Windows users should install the Tesseract executable and language data, then reopen the terminal so `PATH` is refreshed. Scanned PDFs/images use OCR only when direct extraction is insufficient. DOCX is text-extracted; page numbers for DOCX are not reconstructed.

### Optional Chroma and model packages

```bash
python -m pip install -r backend/requirements-optional.txt
```

This installs heavyweight optional ML/vector dependencies (including PyTorch); it is not required for local startup. With Chroma installed, `ENABLE_CHROMA=true` (the default) enables its hashed-token prototype; set it to `false` to stay lexical-only. Set `LEGALBERT_MODEL_PATH` only to a compatible fine-tuned local checkpoint. Without those optional packages/checkpoints, the API uses its lexical/keyword baselines.

### Optional MongoDB / LLMs

To use MongoDB, run a secured MongoDB instance and set `DB_BACKEND=mongodb`, `MONGODB_URI`, and `MONGODB_DB`. To use a hosted LLM, choose `LLM_PROVIDER=gemini` or `groq` and configure the corresponding backend key; Ollama must be reachable from the backend at `OLLAMA_BASE_URL`. Restart the API and verify `/api/v1/health`. Provider failures fall back to evidence-only answers and review checklists; the fallback is not a generated legal analysis.

## Troubleshooting

| Symptom | What to check |
|---|---|
| `ModuleNotFoundError` on startup | Activate the project venv and install `backend/requirements.txt`; run Uvicorn from the repository root using `backend.app.main:app`. |
| API starts but uploaded text is empty | Confirm PDF/DOCX is readable. For scans install Tesseract and the configured language pack; check `/api/v1/health` → `ocr`. |
| `retrieval` reports `local_lexical` | This is expected without Chroma. Install `backend/requirements-optional.txt`, enable Chroma, restart, then re-check health. The hashed-vector mode is still only a prototype. |
| Answers say no LLM is configured | `LLM_PROVIDER=mock` is the safe local default. Configure the provider/key on the backend only, or continue using evidence-only fallback. |
| Flutter reports connection refused | Start the API; serve the Flutter Web build from FastAPI at `/flutter/` so it shares the API origin. For native clients, verify the emulator/simulator address or use a backend LAN/HTTPS address reachable from the device. |
| Browser blocks a cross-origin API request | Prefer the integrated same-origin web app. For separate Flutter Web development, proxy `/api/v1` through the web server to FastAPI; use explicit CORS origins only when cross-origin access is intentional. |
| Upload is rejected | Allowed types are PDF, DOCX, TXT, PNG, JPG/JPEG, and TIFF. Check `MAX_UPLOAD_MB`; password-protected PDFs are not supported. |
| State rule expected but not shown | Only source-review prompts for Maharashtra are currently configured; other state names get a generic stamp-duty verification prompt, not state-law analysis. |
| `flutter create` or package resolution fails | Install a current stable Flutter SDK, run `flutter doctor`, then scaffold runners and run `flutter pub get` inside `frontend/`. |

Keep a tested backup/retention policy for originals and derived data. Do not use a non-persistent container filesystem for user documents.

The current synchronous analysis path and local development defaults are not a scale-out configuration.

# 37. Provider and evidence handling

The backend has a provider adapter for Gemini, Groq, and Ollama, with `mock` as the local default. Provider credentials are read only by the backend. Prompt inputs separate user questions, retrieved contract excerpts, and configured legal review notes. Responses include evidence, related legal-source metadata, provider identity, and limitations; these fields are retained in chat history. Configured provider calls receive up to eight prior messages as conversational context, explicitly not source evidence. The client labels evidence-only fallback separately from provider-generated text, which can still hallucinate and must not be treated as a legal determination.

The local fallback avoids calling a provider and returns retrieved contract evidence with a reminder to consult counsel. Static fallback suggestions are categorized review checklists, not replacement legal wording. An optional provider may produce generated text; that output is clearly distinguishable from deterministic rule findings and classifier signals.

# 38. Output and evidence principles

- Preserve contract/page/clause identifiers, source URLs and titles, source-check dates, ruleset version, trigger terms, and user-selected context where applicable.
- Keep deterministic text triggers, keyword/model predictions, hand-set priority scores, and generated provider text as separate output types.
- Missing evidence must be stated as missing; do not invent provisions, citations, source documents, benchmark results, or legal conclusions.
- A source URL shows where a prompt points; it does not prove the prompt is legally complete or correctly applied.

# 39. Implemented end-to-end workflow

1. An authenticated user uploads a supported file with contract metadata.
2. The API validates and stores the file, extracts text, and records extraction warnings/page count.
3. Heuristic clause segmentation and the configured classifier produce review inputs.
4. Versioned source-review prompts and trigger matches are recorded with provenance.
5. Review-priority indicators and evidence snippets appear in the contract view and PDF report.
6. Chat retrieves contract excerpts; local mode returns evidence-only fallback text. Suggestions are review prompts. Configured LLM adapters may generate responses.

This is a description of the code path, not an example of a tested legal outcome. No sample output scores, statutory conclusions, or model performance are asserted here.

# 40. Chat behavior

A user may ask a question about an uploaded contract. The service retrieves related text and preserves clause/page references where available. In local `mock` mode, the answer quotes/references retrieved evidence and avoids legal interpretation; if evidence is insufficient, it says so. With a configured provider, the answer is generated and may be wrong. No sample contract quote or statutory answer is included in this documentation.

# 41. Suggestion behavior

Without an available LLM, the API returns category-based review checklists (for example, points a reviewer may want to clarify), not substitute clause language. With a configured LLM, generated draft text is still only a drafting aid and requires legal review. Suggestions do not establish that a clause is invalid or that a proposed term is enforceable.

# 43. Known limitations

1. No trained LegalBERT checkpoint or measured classifier performance is included; the default is a keyword baseline.
2. CUAD data are generic contract annotations, not Indian legal coverage. No separate Indian contract example corpus or complete-contract holdout set is registered in this checkout.
3. Legal prompts are narrow and only a small subset of central topics plus Maharashtra source checks are configured. Other state-specific legal coverage is not implemented.
4. Rule triggers depend on text and supplied metadata; omission of a finding is not evidence of compliance.
5. Risk scores are uncalibrated review-priority indicators, not probabilities or legal-risk conclusions.
6. Chroma vectors, where enabled, are deterministic hashed-token features; retrieval has no measured benchmark and is not validated semantic RAG.
7. LLM outputs can hallucinate. External-provider behavior has not been comprehensively tested.
8. OCR, extraction, and heuristic clause boundaries can omit or distort evidence; DOCX pagination is not reconstructed.
9. Upload storage, security controls, operations, Docker deployment, and Flutter runtime require additional validation before real contracts or production use.
10. Stamp duty, registration, employment, procurement, and other rules vary with jurisdiction, instrument, facts, and current law; this prototype does not calculate duty or determine applicability.
